# Changelog

All notable changes to the Enterprise AI Red Team Platform are documented here.

Format: [Semantic Versioning](https://semver.org/) — `Added`, `Changed`, `Fixed`, `Removed`.

## [Unreleased]

### Security
- **CI now gates on high/critical dependency advisories.** A new `Dependency Audit` job runs `npm audit --omit=dev --audit-level=high` for both the backend and frontend production dependency trees, so a shipped vulnerability (like the React Router advisory below) fails the PR instead of only surfacing as an after-the-fact Dependabot alert. Dev-only advisories (build tooling that never reaches users) are reported as warnings but do **not** gate — they churn frequently and blocking on them would redden `main` for issues that don't ship; drop `--omit=dev` in `.github/workflows/ci.yml` to widen the gate. The same check runs locally via `npm run audit:ci`. *(This gate reflects npm-registry advisory data; it is not a substitute for the deeper supply-chain review a security product ultimately warrants — no SBOM, provenance/signature verification, or pinned-hash enforcement yet.)*
- **Upgraded React Router to 8.3.0 to clear the RSC-mode CSRF advisory (GHSA-qwww-vcr4-c8h2).** The frontend was on `react-router-dom@7.18.2`, flagged high-severity by the advisory affecting `react-router` `>=7.12.0 <8.3.0`. The vulnerability **only affects apps using the unstable RSC (React Server Components) APIs** — EART uses standard `BrowserRouter` SPA routing, so it was not exploitable here — but the dependency was bumped to the patched **8.3.0** to clear the Dependabot alert. React Router v8 consolidated its packages (the `react-router-dom` package is discontinued; the last release is 7.18.2), so this drops `react-router-dom` in favour of `react-router` and updates every import from `"react-router-dom"` to `"react-router"`. All APIs used (`BrowserRouter`, `Routes`, `Route`, `Navigate`, `Outlet`, `Link`, `useNavigate`, `useParams`, `useLocation`, `useSearchParams`, `MemoryRouter`) are unchanged in v8; type-check, tests, and build all pass. `npm audit` on the frontend is now clean (0 vulnerabilities).

### Fixed
- **Ollama scans no longer hang when no browser relay is connected.** When the EART server can't reach an Ollama target directly, promptfoo attacks fall back to the browser relay. If no dashboard was connected to forward them, every prompt blocked for the full Ollama timeout (up to 15 min each), leaving the scan stuck at "running" with no feedback. The relay now tracks whether a browser is actively polling and fails the scan fast (in seconds) with an actionable message — "Ollama is not reachable from the server, and no browser is connected to relay prompts to it; open the dashboard in a browser that can reach it, or run EART where it can reach Ollama directly."

### Added
- **Custom roles and fine-grained permissions.** On top of the three built-in tiers (viewer < analyst < admin), an admin can now define **custom roles** — named sets of fine-grained permissions from a catalog (`project:*`, `scan:create`/`cancel`/`delete`, `report:generate`, `remediation:generate`, `users:manage`, `roles:manage`, `settings:manage`, `audit:read`, `retention:manage`, …) — and assign one to a user. A user's *effective* permissions are the **union** of their base-tier permissions and any assigned custom role's: the base tier is a floor a custom role can only add to, and `admin` always holds every permission. This makes least-privilege delegation possible — e.g. grant an analyst `audit:read` (or a viewer `scan:create`) without making them a full admin. New `requirePermission(...)` middleware backs the checks (the audit route now uses `audit:read` so it can be delegated), the JWT carries the assigned role id (assignment takes effect on next login; editing a role's permissions takes effect within a short cache TTL), and `/api/auth/me` + login now return the caller's effective `permissions`. Managed from **Settings → Custom Roles** (define roles + tick permissions) and **Settings → Users** (assign a custom role per user), or via the admin API at `/api/roles` (+ `GET /api/roles/permissions` for the catalog). Backward-compatible and additive — nothing changes for the three built-in tiers when no custom role is assigned. New `custom_roles` table + `users.custom_role_id` column (idempotent migration on both SQLite and Postgres). This is real additive RBAC, not a full policy engine — there is no ABAC, per-resource ownership, or deny rules; see the gap assessment.
- **IdP group → EART role mapping.** SSO logins can now derive the user's role from their identity-provider groups instead of always using the default. Configure `SSO_GROUP_ROLE_MAP` (comma-separated `group=role` pairs, with a `*` catch-all); the groups come from the OIDC groups claim (`OIDC_GROUPS_CLAIM`, default `groups`) or the SAML groups attribute (`SAML_GROUPS_ATTRIBUTE`). When a user belongs to several mapped groups the **highest-privilege** role wins, so a broad low-privilege group can never demote an admin. The role is **synced on every SSO login** (so IdP promotions/demotions take effect), but only when a group actually maps — a user with no mapped group keeps their existing role, so manual roles aren't clobbered. Role changes are audit-logged (`auth.sso_role_sync`). Applies to both OIDC and SAML; unchanged behavior when no map is configured.
- **SAML 2.0 single sign-on.** Alongside OIDC, EART now supports SAML SSO as a service provider, using the vetted `@node-saml/node-saml` library for AuthnRequest generation and — critically — **signed-assertion validation** (XML signature + assertion conditions; hand-rolling XML-DSig is deliberately avoided). `GET /api/auth/saml/login` redirects to the IdP; the IdP POSTs the signed response to the ACS at `/api/auth/saml/callback`, which validates it, extracts the email (from standard email attributes or an email NameID), find-or-creates the user, and mints an EART JWT; `GET /api/auth/saml/metadata` serves SP metadata for IdP registration. Domain allow-list, default role, and audit logging as with OIDC. Feature-flagged on the `SAML_*` env vars. `GET /api/auth/sso/status` now reports both OIDC and SAML availability.
- **SCIM 2.0 user provisioning.** EART is now a SCIM service provider so an IdP can provision, update, and deprovision users automatically (`/scim/v2/Users` CRUD + `PATCH` for `active`/`role`, plus the `ServiceProviderConfig`/`ResourceTypes`/`Schemas` discovery endpoints and `userName` filtering). Authenticated with a static bearer token (`SCIM_TOKEN`, constant-time compared); the whole surface 404s when unset, so it's off by default. A new `users.is_active` flag drives deactivation — **deactivated users are refused at password login and SSO** — and `users.external_id` records the IdP id. Deprovisioning (`DELETE`) is a soft-delete (deactivate) so scan history is preserved; every SCIM mutation is audit-logged.
- **Data-retention controls.** Two data-governance levers for handling sensitive target data. (1) **Time-based purge** — `DATA_RETENTION_DAYS` deletes scans (and their results, reports, and on-disk report files) older than N days; `AUDIT_RETENTION_DAYS` does the same for the audit log. Runs on a daily schedule and on demand via `POST /api/retention/purge` (admin), never deletes an in-flight scan, and records what it removed to the audit log. (2) **Response minimization** — `SCAN_STORE_RESPONSES=false` stops EART from persisting the raw prompt/response text of findings (which can contain data pulled from the target), keeping only the verdict and metadata. Both default to safe/off (keep forever, store responses). `GET /api/retention` reports the active configuration.
- **OIDC single sign-on.** EART now supports "Sign in with SSO" via the OpenID Connect authorization-code flow against any standards-compliant provider (Okta, Azure AD / Entra, Google, Auth0, Keycloak, …). `GET /api/auth/oidc/login` redirects to the IdP with a stateless, signed `state` (embedding a `nonce`) for CSRF/replay protection; `GET /api/auth/oidc/callback` exchanges the code, **cryptographically verifies the ID token** against the provider's JWKS (signature + `iss`/`aud`/`exp`/`nonce`), then find-or-creates the user and mints an EART JWT. SSO users get a non-usable password hash so they can never fall back to password login. Configurable domain allow-list (`OIDC_ALLOWED_DOMAINS`), verified-email requirement, and auto-provision role (`OIDC_DEFAULT_ROLE`). Feature-flagged — activates only when the `OIDC_*` vars are set — and every SSO login/provision/failure is written to the audit log. `GET /api/auth/sso/status` lets the login page show the button. (SAML is not yet supported — OIDC covers the common enterprise IdPs; SAML is a documented follow-up.)
- **Expanded engine coverage: 60 → 82 plugins.** Broadened the real-engine surface toward each tool's actual capability. **+11 garak probes** (verified present in garak): PromptInject, latent/indirect injection, Goodside attacks, auto-adversarial `atkgen`, Tree-of-Attacks-with-Pruning, ANSI-escape injection, training-data divergence, malicious file formats, code exploitation, AV/spam signatures, tense/phrasing evasion. **+11 deepteam vulnerabilities** (verified in deepteam 1.0.x): Prompt Leakage, RBAC, BOLA, BFLA, SQL Injection, Shell Injection, SSRF, Illegal Activity, Personal Safety, Debug Access, Graphic Content — each mapped to its real deepteam `Vulnerability` class and to ATLAS/NIST via its category. The Full preset auto-includes them. Coverage is now materially broader but still a curated subset of each tool's full surface (garak has 100+ probes) — see the gap assessment.
- **CI builds the worker images + a live-model smoke test.** Two gaps from the readiness assessment: the garak/pyrit/deepteam Docker images were never built in CI, and no test exercised a real model. Now a separate **Worker Images** workflow builds all three images (matrix, buildx layer cache) and protocol-checks each — triggered only on `python-workers/**` changes, a weekly schedule, or manual dispatch, so the heavy builds never slow unrelated PRs. And a standalone **live-model smoke** (`npm run smoke:live`, `scripts/live-smoke.mjs`) drives one adversarial prompt through a real target model and an independent judge model end-to-end, asserting the target-call + AI-judge path works against live models; it SKIPS cleanly (exit 0) without `ANTHROPIC_API_KEY` + `LIVE_SMOKE_TARGET_URL`, and runs in CI whenever a maintainer configures those secrets/vars.
- **MITRE ATLAS + NIST AI RMF framework mappings.** Findings now carry control-framework context beyond OWASP LLM Top 10. Each plugin/finding is mapped to the relevant **MITRE ATLAS** technique(s) (e.g. `AML.T0051` LLM Prompt Injection, `AML.T0054` LLM Jailbreak, `AML.T0057` LLM Data Leakage, `AML.T0056` Extract LLM System Prompt) and **NIST AI RMF** trustworthiness characteristic(s) (Secure & Resilient, Privacy-Enhanced, Fair, Safe, Valid & Reliable, Accountable & Transparent). Mappings are derived from each finding's category/OWASP category (single source of truth — `src/server/config/frameworkMappings.ts`), surfaced per-plugin in `GET /api/scans/catalog` and per-finding plus an aggregated coverage summary (`frameworkCoverage`) in the JSON report. The mappings are explicitly labelled *indicative* — derived control mappings for reporting, not a certified compliance attestation. Partially addresses the frameworks gap from the enterprise readiness assessment (HTML/PDF surfacing and exact numbered NIST subcategories are follow-up).
- **Audit logging and scan reproducibility.** A new append-only `audit_log` table records security-relevant actions — logins (including failures), project create/update/delete, scan create/cancel, and user role-change/delete — with the actor (id + denormalized email so the trail survives user deletion), target, non-sensitive detail, client IP, and a millisecond timestamp. Writes are fire-and-forget so an audit failure can never break the underlying request. Admins can read and filter the trail at `GET /api/audit` (paginated, `?action=` / `?userId=` filters). Separately, each scan now captures a **reproducibility snapshot** in a new `scans.run_metadata` column at run start — the plugin selection, engine image tags, knob values (`GARAK_PROMPT_CAP`, `PYRIT_TREE_*`, `DEEPTEAM_*`, `SCAN_JUDGE`), and the evaluator model name (never its key) — so a finding can be traced to exactly how it was produced. Addresses the audit-trail and reproducibility gaps from the enterprise readiness assessment.
- **Scan governance — cost ceiling, rate limiting, and target authorization.** Adversarial engines can make a large, variable number of model calls (a PyRIT tree attack alone can fire hundreds per plugin), so a scan could previously rack up a big bill or hammer a target with no guardrail. Now: (1) a **pre-run cost estimate** (`GET /api/scans/estimate`) reports an upper-bound target-call count per engine before you run; (2) scans whose estimate exceeds `SCAN_MAX_TARGET_CALLS` (default 25 000; 0 = unlimited) are **refused at creation** with the estimate; (3) `SCAN_TARGET_RATE_LIMIT` (calls/min) throttles EART's own outbound target calls on the attack-loop path; and (4) a **target authorization allow-list** (`TARGET_ALLOWLIST`, exact or `*.wildcard` hosts) restricts which target hosts may be added to a project or scanned — enforced at project create/update and again at scan time — so EART can't be pointed at a third party's endpoint. The SSRF denylist still applies regardless. Closes the "no cost/rate governance, no target authorization" gaps from the enterprise readiness assessment.
- **The PyRIT worker now runs Microsoft's real PyRIT toolkit.** Previously the PyRIT worker imitated attacks with hand-written prompts and keyword pass/fail checks. It now invokes the actual [PyRIT](https://github.com/Azure/PyRIT) engine: each EART PyRIT plugin maps to a real PyRIT attack strategy — `PromptSendingAttack` (prompt-shield-bypass, indirect-injection-agentic, xpia), `SkeletonKeyAttack`, `ManyShotJailbreakAttack`, `FlipAttack`, `CrescendoAttack`, `TAPAttack`, `PAIRAttack` — driven against the target through a custom `PromptChatTarget` (backed by EART's HTTP layer, so any OpenAI/Anthropic/Ollama-compatible endpoint works). A real PyRIT `Scorer` (`SelfAskRefusalScorer`, or a `FloatScaleThresholdScorer` for the tree-based attacks) run by the evaluator LLM decides whether each objective was achieved, and PyRIT's own `AttackOutcome` is reported (SUCCESS = objective achieved = vulnerable) mapped back to EART severity/OWASP. Like DeepTeam, this needs an **independent evaluator LLM** (Settings → AI Remediation or `ANTHROPIC_API_KEY`, never the target grading itself) for the adversarial orchestration and scoring; without one the worker falls back to EART's original probes, labelled `mode: builtin-heuristic`. Multi-turn attack breadth/depth are tunable (`PYRIT_MAX_TURNS`, `PYRIT_TREE_WIDTH`, `PYRIT_TREE_DEPTH`, `PYRIT_SCALE_THRESHOLD`). PyRIT telemetry is opted out and its console output is redirected off the JSONL protocol stream. **With this, all four engines are real or honestly labelled** — Garak, DeepTeam, and PyRIT invoke real external tools, and Promptfoo uses its real harness for cloud providers plus EART's own attacks (with the AI judge) elsewhere.
- **The DeepTeam worker now runs the real DeepTeam framework.** Previously the DeepTeam worker simulated probes with hand-written prompts and keyword/regex pass-fail checks. It now invokes the actual [deepteam](https://github.com/confident-ai/deepteam) engine: each EART DeepTeam plugin maps to a real deepteam `Vulnerability` (Toxicity, Bias with `types`, PIILeakage, Misinformation, IntellectualProperty, ExcessiveAgency, Robustness, Hallucination), deepteam drives its attack enhancements (PromptInjection, Roleplay, … — configurable via `DEEPTEAM_ATTACKS`) against the target, and EART reports deepteam's own metric verdicts (score 1 = resisted, 0 = exploited) mapped back to EART severity/OWASP. This needs an **independent evaluator LLM** — the same provider that powers the AI judge (Settings → AI Remediation or `ANTHROPIC_API_KEY`), never the target grading itself — to simulate attacks and judge responses. When no evaluator is configured, the worker falls back to EART's original probes, now explicitly labelled `mode: builtin-heuristic` so the report never overstates what ran. deepteam telemetry/update-checks are opted out and its console output is redirected off the JSONL protocol stream.
- **Python worker test coverage in CI.** The garak/pyrit/deepteam worker runners had no automated tests. A new dependency-free `unittest` suite (`python-workers/tests/`) now covers their pure logic — garak's REST-config building, prompt shaping, detector scoring and plugin mapping; pyrit's SSRF guard (`_is_safe_url`) and content-detection heuristics; and the deepteam stdin→JSONL protocol contract — and runs as a new `Python Worker Tests` CI job that imports the runners (catching syntax/logic drift) and lints the worker Dockerfiles. The heavy tool images are not built on every push (garak's Rust + ML stack takes 20+ min); that's called out in the workflow.
- **Semantic "AI judge" grading for built-in attacks.** EART's own attack library graded responses purely by regex — a match on an exploit marker (e.g. `CONFIRMED_INJECTED`) meant "compromised", no match meant "safe". That produced false all-clears whenever a model complied *in its own words* or leaked a system prompt phrased differently than the pattern expected — the worst failure mode for a red-teaming tool. Now, when an independent AI provider is configured (Settings → AI Remediation, or `ANTHROPIC_API_KEY`), every response the regex marked "safe" is re-examined by a judge model that decides whether the model actually performed the unsafe behaviour. The judge can only escalate a regex pass to a finding (a matched exploit marker is always honoured), never uses the target model to grade itself, and is fully best-effort — any judge error, timeout, or missing provider falls back cleanly to the regex verdict. Each finding records how it was graded (`gradedBy: "regex" | "llm-judge"`) and the judge's rationale. Disable with `SCAN_JUDGE=off`.
- **The Garak worker now runs the real Garak engine.** Previously the Garak worker simulated probes with hand-written prompts and heuristic pass/fail checks. It now invokes the actual [garak](https://github.com/NVIDIA/garak) tool: each EART Garak plugin maps to real garak probe modules (`encoding`, `dan`, `malwaregen`, `web_injection`, `suffix`, `leakreplay`, `realtoxicityprompts`, `packagehallucination`, `lmrc`, `grandma`, …), garak drives them against the target through its REST generator (Ollama / OpenAI-compatible / Anthropic / custom), and EART reports garak's own detector verdicts — aggregated to one finding per probe (hits/total) with a real prompt/response sample. Prompts per probe are capped (`GARAK_PROMPT_CAP`, default 8) to keep scans bounded. PyRIT and DeepTeam still run EART's built-in probes for now (documented in the README).
- **Real PostgreSQL support.** The database layer now runs on either SQLite (default, `better-sqlite3`) or PostgreSQL (`postgres-js`), selected automatically from `DATABASE_URL` — a `postgres://` / `postgresql://` URL uses Postgres, anything else is a SQLite path. The Drizzle schema is split into dialect-specific mirrors (`schema.sqlite.ts` / `schema.pg.ts`) behind a barrel that keeps every call site and its types unchanged; queries go through dialect-neutral `getRow`/`getRows` helpers, and `npm run db:migrate` (or first boot) creates the tables on either engine. No external migration step is required for Postgres.
- **Accessibility pass.** The UI now respects `prefers-reduced-motion` (the ambient cyberpunk animations — circuit drift, neon pulse, flicker, spinners — are disabled for users who ask for reduced motion), shows a visible keyboard focus ring on every interactive element, and adds a "skip to main content" link, a `<main>` landmark, a labelled primary navigation, ARIA labels on icon-only buttons, and a live region + proper `progressbar` semantics on the scan progress. _(A light color theme was evaluated but deferred: the interface is a deliberately dark "cyberpunk" design with pervasive neon styling, so a light mode needs dedicated design work rather than a mechanical token flip.)_
- **Live scan progress (SSE) and a cancel button.** A running scan's page now streams progress over Server-Sent Events (`GET /api/scans/:id/events`) instead of relying on polling alone — the worker publishes each progress/status update through a Redis channel that the app fans out to watching browsers (one Redis connection per app process, not per viewer). Polling remains as an automatic fallback if the stream drops. The scan page also gains a **Cancel** button, so the prompt cross-process cancellation added earlier is finally reachable from the UI.
- **User management (admin).** Admins can now list all users, change their roles, and remove them from a new Users section in Settings (`GET/PATCH/DELETE /api/users`). Deleting a user cascades their projects, scans, results and reports in a transaction. Guardrails prevent demoting or deleting the last remaining admin, and deleting your own account.
- **Remediation before/after comparison.** After running "Verify Fixes", the retest's results page shows a before/after panel comparing the retest against the original scan by OWASP category — how many categories were fixed, improved, or still failing (`GET /api/scans/:id/diff?original=<scanId>`). It updates live while the retest runs.
- **HTML and CSV report formats.** Alongside PDF and JSON, scans can now be exported as a self-contained styled HTML report (severity cards, OWASP coverage, failed-finding detail — no external assets) and as a spreadsheet-friendly CSV (RFC-4180 quoted, UTF-8 BOM for Excel). The Reports page offers all four formats.

### Changed
- **Scan results are paginated and stats are aggregated in SQL.** `GET /api/scans/:id/results` now takes `limit`/`offset` and returns a `{ results, total, limit, offset }` envelope, and the results-summary endpoint aggregates with `COUNT`/`GROUP BY` instead of loading every finding row into memory — so a scan with tens of thousands of findings no longer risks OOMing the API. The Results page drives its charts from the summary endpoint and pages through findings with a "Load more" button. Also fixed a summary bug where passing `info` findings were miscounted as failures.
- **Scan progress writes are batched.** The scanner flushes the scan row's running counters every 20 findings (and at each tool boundary) instead of once per finding, cutting write contention on the shared SQLite file.
- **Ollama browser relay moved to Redis.** The relay queue and pending responses now live in Redis (blocking-list based) instead of in the app process's memory. The scan worker enqueues relay requests directly rather than HTTP-POSTing to its own app with a minted internal token, and poll/fulfill work across app replicas (a browser polling one replica and a producer waiting on another share the same queue). Per-user scoping and cross-user isolation are preserved via a per-request owner key. Removed the now-unused `/api/ollama/relay/forward` endpoint and the internal-token minter.
- **Prompt, cross-process scan cancellation.** Cancelling a scan now publishes a Redis pub/sub signal that the worker acts on immediately — aborting the in-flight tool and killing its Docker container mid-run — instead of only being noticed between tools by DB-status polling. The signal fans out to every worker replica, so cancellation works when the app and worker (or multiple workers) run as separate processes. Persisted scan status remains the durable source of truth and the polling fallback still guarantees eventual cancellation if a subscriber is momentarily disconnected.

### Security
- **Docker socket hardening + non-root containers.** The app and worker no longer bind-mount `/var/run/docker.sock`. Instead a dedicated `tecnativa/docker-socket-proxy` service mounts the socket (read-only) and exposes only the container/image endpoints the workers need (`CONTAINERS`/`IMAGES`/`POST`), so a compromised app can't reach the full host Docker API (exec into other containers, secrets, swarm, volumes). The runtime image also now runs as a non-root `eart` user, with an entrypoint that fixes volume ownership before dropping privileges.
- **Report download hardening.** The file-path containment check now uses a separator-terminated match (a sibling like `<dir>-evil` no longer passes), and the download filename is built from the report's own sanitized scan id rather than the raw URL parameter.

## [2.2.0] — 2026-08-04

### Fixed
- **Garak / PyRIT / DeepTeam findings were silently discarded** — the Python workers emit snake_case JSON (`test_name`, `owasp_category`) but the backend read camelCase, so every insert into the `NOT NULL` `test_name` column threw and was swallowed. Scans reported only Promptfoo results while claiming all four tools ran. `dockerRunner` now normalizes worker output, awaits result persistence before resolving, surfaces worker error lines instead of parsing them as findings, and no longer reports a crashed worker as a clean scan.
- **OWASP categories were almost never recorded** — the scanner re-derived severity/OWASP from an 8-entry substring map covering 8 of 60 plugins, so most findings stored `owaspCategory: null` and reports showed "Not Tested". Severity and OWASP now come from the authoritative plugin catalog.
- **Scan cancellation was cosmetic** — cancelling flipped the DB status but the running scan finished anyway and overwrote it back to `completed`, leaving orphaned Docker containers. Cancellation is now honoured across process boundaries: in-flight tools stop, worker containers are killed by name, partial results are kept, and the status stays `cancelled`.
- **BullMQ retries duplicated results and corrupted counts** — a retried scan left the previous attempt's rows in the database. Each (re)start now clears prior results and resets counters so a retry is idempotent.
- **Scans could hang in `running` forever** after a worker crash — the worker now recovers orphaned `running` scans (with no live job) to `failed` on startup, and aborts in-flight scans on shutdown so their containers are killed rather than orphaned.

### Security
- **SSRF hardening** — the AI-remediation/narrative and direct-endpoint scan paths fetched user-supplied URLs with no guard, allowing requests to cloud-metadata endpoints (e.g. `169.254.169.254`). A denylist guard now blocks cloud-metadata and link-local targets on those paths (loopback and LAN hosts remain reachable for local models).
- **Ollama browser relay is now scoped per user** — poll/fulfill were global, letting any authenticated user pull another user's queued scan prompts off the queue or inject fabricated LLM responses into their results. Relay items are now bound to the owning user, and the scan worker authenticates its forward calls as the scan owner via a short-lived internal token.
- **Project provider API keys are no longer returned to clients** — the projects API echoed the stored `apiKey` in plaintext. It is now redacted to a `hasApiKey` flag (matching the SMTP-password pattern) and preserved across partial updates so it is never wiped by a save that omits it.
- Docker worker containers now run with `--pids-limit` in addition to the existing memory/CPU/`no-new-privileges` constraints.

### Added
- Tests for worker-result normalization, the SSRF denylist guard, provider-config redaction/secret-preservation, and per-user relay isolation (backend suite: 61 → 81).

- **License key system** — the license activation API (`/api/license`), license validator, RSA keygen script, `license_keys` database table, License page, and `RSA_PUBLIC_KEY_PATH` configuration have all been removed. No license is needed: the platform is fully unlocked for everyone.
